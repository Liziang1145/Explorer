# AIPC / KR260 核心指标测量：实现、边界与实机操作

日期：2026-11-02。入口：<http://192.168.137.2:8091/core-metrics.html>。沿用AIPC登录，统一侧栏“核心指标测量”。

## 已上线与自动执行

- 实时CPU曲线、网卡/CAN区间计数与有效数据速率；保留原始计数，不清零驱动统计。
- 同接口、同CAN ID、同方向的内核软件时间戳间隔、P50/P95/P99/最大值，间隔标准差及相对中位数绝对偏差P95。
- 独立UDP往返探针（5 Hz）、独立鉴权HTTP时钟探针（1 Hz）、超时/往返丢失与RTT变化。
- 限载20 Mbit/s、双向各60秒的TCP有效载荷测试。每方向实际字节数除以实际持续时间，附逐秒数据和SHA256验证；两方向顺序执行。这不是千兆饱和性能或PL转发能力。
- 手动VR→双臂响应测试，开始、停止、历史任务、分段分布、逐次原始数据、报告MD下载。正式环境未进行戴VR运动，页面不伪造端到端分位数。
- 默认总计50,000,000,000字节原始证据预算，FIFO循环保留，分片SQLite数据库。无需网页打开即可继续自动采集。

本服务不会发送CAN控制帧，不启用CAN2，不变更FPGA位流、网口配置、机械臂安全逻辑、使能位或目标位置。网络探针使用独立端口，不注入机械臂的54321/54322控制端口。

## 先认识当前真实实现

| 部分 | 当前实现 | 可归属的贡献 |
|---|---|---|
| `FPGA_CAN0` / 左臂 | PS `ff060000.can`，`xilinx_can` | PS硬CAN控制器、Linux SocketCAN驱动，经PL路由到J20 |
| `FPGA_CAN1` / 右臂 | PS `ff070000.can`，`xilinx_can` | 同上；命名FPGA_CAN不等于控制器位于PL |
| `FPGA_CAN2` | PL `80160000.can`，CTU CAN | 开源PL CAN逻辑；当前DOWN，未自动开启/发帧 |
| eth0 / eth1 | PS GEM | 实际AIPC↔板卡终止流量经eth0；管理口eth1独立 |
| eth2 / eth3 | PL MAC，`xaxienet` | PL提供网络接入和可修改的MAC/复位/调试逻辑 |
| br-fabric | Linux bridge | 当前二层转发仍包含PS软件路径，不能说已实现PL交换卸载 |
| 后台、DHCP、配置回退、服务管理 | PS Linux软件 | 独立板端运维能力；不是PL硬件加速贡献 |

在本次读取时，AIPC网卡eno1只有软件时间戳、没有PHC；KR260 eth0支持硬件时间戳且有ptp0，但这不意味着两端已经组成硬件PTP同步。

### 普通CAN转接板、交换机或软件能否替代

不能以当前工程数据证明“绝对不能替代”。普通CAN板可替代部分CAN收发，普通交换机可替代部分二层交换，普通Linux主机也能运行管理后台与Linux桥。

KR260平台的工程价值在于集中部署、独立管理、PS硬控制器与定制PL接口的一体化，以及PL可增加协议并行处理、纳秒/周期级统一计数、ILA观测和局部复位的扩展空间。更换普通设备不等于可以原样保留定制引脚、AXI寄存器、复位/观测通路和已有驱动接口；但适配后的替代方案并非原理上不可能。

当前尚无相同负载、同样端点、同样电气接线的USB-CAN/普通交换机/纯软件基线对照。因此不报告“快多少倍”“CPU降低多少”或确定性最坏时延保证。管理后台的优势属于系统集成与维护性，不是与专业交换机对比的硬件转发性能结论。

## 手动实机测量步骤

1. 确保VR连接AIPC；确认双臂有正常编码器反馈、收发器/终端电阻接好，场地和禁区安全。
2. 在本页“VR→机械臂”填写名称、任务时长、角度阈值，点击开始。这只建立观察任务和本机只读埋点开关，不申请控制权、不使能。
3. 在现有机器人控制页面按原流程使能、取得控制权，再戴VR操作。不要同时运行另一个控制器/同事的测试程序。
4. 为测响应起点，每次动作前保持静止至少0.5秒，随后做一次明确的小幅动作并再次静止。左右臂可分别测量。连续运动不能解释成每个控制包的一次独立响应。
5. 点结束，或等待任务时长结束。页面显示N、P50/P95/P99/最大值、失配及超时；下载报告MD，原始记录通过任务ID导出。最多一小时或10000个响应样本，先到者结束。

建议至少采集100次以上独立动作以观察P99，若希望稳定估计尾部还应更多。低N的P99几乎就是最大值，报告保留N，不把少量样本当作稳定性能保证。

### 起点、终点与精度

起点是现有VR协议的 `origin_ns`：控制输入样本的软件时间戳。它不是物理手指开始按键或光学追踪第一次探测动作的外部触发时间。

当前可用终点是**同轴编码器相对静止基线首次越过设定阈值**，并由后续同轴连续3帧确认；最终使用首次越过时刻，附原始包。它是机械臂运动反馈代理，包含编码器上报周期、总线与接收调度。不能把TX成功、本地回显、收到使能ACK或目标值变化当成真实机械运动。

严格“机械臂物理开始移动”的延迟需接同步编码器触发、光电/IMU等外部传感器，并明确检测阈值。当前页面明确区分代理与严格物理终点；没有外部触发时不声称已完成严格物理起动验收。

### 分段公式与相加边界

| 段 | 边界与实现 | 注意 |
|---|---|---|
| VR→AIPC | 映射后的VR origin → AIPC `a_rx_ns` | TLZ epoch与映射必须有效，否则该段留空 |
| AIPC排队/消费 | `a_rx_ns` → 对应VR版本IK提交 | 包含25ms轮询、滤波与消费等待，不只是网络 |
| IK | 提交 → 版本/安全复核后接受该解 | 异步最新槽被覆盖的输入不会伪造为执行样本 |
| 发送等待 | 接受IK → 实际UDP sendto后埋点 | 包含20Hz发送调度与极短埋点位置误差 |
| AIPC→KR260 | 本机UDP发送埋点 → eth0观察接收 | 四时间戳软件映射估计，保存不确定度 |
| 板端到CAN | UDP观察 → 对应臂随后首次TX本地回显 | 包含PS规划、驱动和CAN路径；仅时序关联，不能归因PL或当成执行端逐命令确认 |
| CAN到反馈 | 首次TX回显 → 编码器越阈值 | 包含执行器、反馈周期和观察延迟 |

同机时段分别使用各自主机单调时钟作差，再相加。跨机器的网络段不会因“使用相对时间”自动变得可测：需要同步/时钟映射，或者改用同一主机计时的RTT。不能把缺失网络段默认为0，也不把RTT/2当作真实单向延迟。

软件时钟探针使用t1(A发)、t2(K收)、t3(K回)、t4(A收)。`RTT=(t4-t1)-(t3-t2)`；偏移估计为 `((t2-t1)+(t3-t4))/2`。采用近期最低RTT映射，保留RTT/2加1ms余量的不确定度和boot ID；不调整系统时钟，不影响原NTP。缺失、过期、epoch改变或时序异常会计入失配，不生成伪造完整样本。

VR映射复用 `/run/tlz-aipc/adapter.sock` 的 `/pose-context`、`/health`，读取VR和AIPC到TLZ基准时钟的映射；检查源epoch及2秒新鲜度。无法建立有效VR映射时，全链路分布N为0，仍可报告AIPC接收之后的部分链路。

UDP seq精确关联AIPC发送和板端收到的142字节现有帧。**CAN帧未携带这个seq**，所以当前末端使用“静止后的响应起点时序关联”，不是完全的逐指令因果跟踪。重叠目标、持续动作、其他控制源或传感器噪声都可能使关联不成立；页面显示原始证据、失配与限制。要进一步细分到规划器输出、驱动入队、控制器SOF以及机械动作，需由执行端/PL增加明确trace和统一计数器埋点。

## 网络、CAN、丢失与抖动的口径

- UDP探针丢失：同序号往返未在250ms内成功返回的比例，不能区分去程与回程；旧/晚包不计为当前成功。不等同实际机械臂指令丢包。
- HTTP超时：独立测试服务的应用探针失败比例，含建连、鉴权、调度和服务不可用；不是实际执行器指令超时率。
- 当前控制协议无逐命令执行ACK，因此真实“执行指令超时率”留为未测；不能用独立探针替代。
- TCP有效吞吐：完整payload字节/完整实际耗时，含协议与调度影响，附逐秒记录、方向与限速。SHA256完整性验证的是整个payload，不是逐包比特误码率。
- 重传：`/proc/net/snmp` RetransSegs/OutSegs区间增量，属于整机所有TCP连接，不能冒充本次测试连接专属重传率。
- 网卡drop/error：驱动计数增量及相应分母，和端到端丢包分开。历史累计错误不当作新故障。
- CAN吞吐：sysfs的数据域字节/区间时长、帧数/区间时长；不包含总线仲裁、CRC、填充和重试位。
- CAN抖动：同接口、同CAN ID、同方向的内核软件时间戳间隔，报告间隔标准差及相对中位数绝对偏差的P95。无硬件SOF时间戳，不声称逻辑分析仪级精度。
- 以太网抖动：连续UDP探针RTT绝对差的分布；包括端点调度，不称为PL内部转发抖动。
- CPU：系统 `/proc/stat` 各核归一化占用，另列测量进程单核CPU比例。100%单核不等于整机100%。原始计数可重算。

eth1无链路、CAN2 DOWN时不会主动拉起接口或用内部回环伪装外部验收。PL网络处理延迟、PL CTU CAN逐帧处理延迟和AXI持续吞吐尚缺可验证硬件埋点/对端，页面明确“未测”。

## 数据库与部署

- AIPC采集服务：`core-metrics.service`，`/home/apex/core-metrics/`，本机127.0.0.1:18261。
- KR260只读观察服务：`core-metrics-peer.service`，`/opt/core-metrics/peer.py`，192.168.137.1:18260及UDP18262。仅接受AIPC源地址和随机鉴权令牌；令牌文件不可发布到文档或网页。
- 总数据库目录：`/home/apex/core-metrics-data`。catalog.sqlite3保存任务；e2e/fpga/communication分片保存原始记录。分片约16MiB/30分钟滚动，硬总预算50GB，并考虑磁盘余量。
- 三项目权重为实存编码字节加记录开销的平均值，用指数更新；目标是各项目保留相近数量的记录。加权份额是软配额，总量触发回收时优先删除超份额项目最早分片，再全局FIFO。冷项目未用份额不提前浪费。
- 原始时间戳、接口累计计数、逐包CAN数据、控制UDP、RTT四时间戳、吞吐窗口、任务事件与响应证据都入库。仅大记录使用zlib，无损可还原。
- FIFO影响原始分片；历史任务摘要可能仍存在，但原始证据已过期。导出只包含当时仍保留的数据，不承诺超预算永久保存。
- 背景线程以低优先级运行；不在控制线程中写库。AIPC控制旁路使用非阻塞Unix datagram，测量失败不停止/改变控制。只在手动任务开关存在时发出埋点。
- 板端使用只读原生C++ SocketCAN接收器，每批最多256帧，以小端定长二进制送到Python，再传给AIPC解码入库；不在板端逐帧JSON编码。CAN仅采集本次分析所需的控制/反馈ID：0x155～0x15F、0x251～0x256、0x2A5～0x2A8及选定错误帧；并非整条总线的无过滤全量录包。接口吞吐仍来自全接口计数。以太网只抓现有控制端口，内核BPF过滤视频/雷达；内存有界。CAN socket溢出及观察队列覆盖单独记录为采集损失。

部署前已备份原后台和机械臂控制文件：`/home/apex/backups/core-metrics-1793629097`。只为载入只读旁路，在核对双臂会话都不活动后重启了arm-console；未重启deploy、未改变控制/IK算法、网络/CAN参数或位流。相机、雷达、TTS、LLM不在本次修改范围。

## API与后续SDK

公网管理前缀 `/api/v1/core-metrics`，需现有AIPC会话；POST需 `X-Hub-Client: console` 和同源Origin。浏览器不持有板端随机令牌。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/status` | 当前状态、百分位、趋势、任务、存储份额、能力限制 |
| GET | `/raw?project=e2e或fpga或communication&limit=100` | 最近原始记录，单次最大2000 |
| GET | `/export?project=e2e&task_id=任务ID` | 当前保留的原始NDJSON，流式下载 |
| GET | `/report?id=任务ID` | 手动测试/吞吐报告MD |
| POST | `/trial/start` | `{name,duration_s,threshold_deg}`，只启动测量 |
| POST | `/trial/stop` | `{}`，结束并保存统计 |
| POST | `/throughput/start` | `{seconds,rate_mbps}`，每方向10～120秒，1～50Mbit/s |

下一步若执行端/PL增加trace，统一事件至少包含：schema版本、boot ID、节点/时钟域、trace ID、原命令seq、side、stage、单调时间戳、边界定义、不确定度及实际原包。只允许把同一事务/同一轴的关联阶段相减。外部物理触发需要与CAN/网络计数器同步，不可使用浏览器点击时间代替。
