# 建图、导航、语义与 VR 三路产物链路交付

更新日期：2026-11-03。目标机器：AI PC `192.168.6.206`。本次只进行保存数据的离线处理、服务部署和任务草稿验证，没有开启实车采集，没有发送底盘或机械臂运动命令。

## 1. 本次改动解决什么问题

此前导航派生等待 `dense-color-v1/ready.json`，也就是必须等全量重放、着色完成。导航发布时还生成了空语义场景，导致新地图与旧语义页、本地千问的数据不一致。

现在结束采集后，处理分成独立的工作进程：

```text
LiDAR / IMU / RGB-D / 鱼眼 → 独立原始记录，完整保留
                  │
                  ├─ 原车 FAST-LIO 在线建图的配准点与轨迹
                  │      → 10 cm 导航轻量几何 → 导航栅格 / 定位参考 / 矩形通行模型
                  │      → 离线定位及路线校验 → 通过现有联锁选择场景
                  │
                  ├─ 同次 RGB-D + 同一份在线轨迹 + 冻结的建图标定
                  │      → YOLO + 深度融合 → 物体、邻近关系、原图证据
                  │      → 当前场景语义 → 本地千问草稿 / 前提检查 → 原导航执行接口
                  │
                  └─ 原始记录离线密集重放
                         → RGB-D 优先着色，鱼眼补充
                         → 全量密集彩色点云 + 5 cm 轻量彩色点云
                         → 既有 VR 分块打包与传输服务
```

正式导航仍复用原车 FAST-LIO 工程。FAST-LIVO2 研究没有替换当前定位器。

## 2. 三种产品的明确用途

| 产品 | 默认策略 | 用途 |
|---|---|---|
| 导航无颜色几何 | 每帧 10 cm 体素保留实际观测点；最高 5 Hz 几何帧；全部位姿保留 | 快速生成导航地图、定位参考、矩形路线 |
| VR 全量密集彩色点云 | 沿用全量重放策略；没有新增总帧数或总点数截断 | AI PC 保存完整可着色场景，供近处精细分块 |
| VR 轻量彩色点云 | 从全量产品派生 5 cm 版本 | VR 全局粗场景与远处显示 |

导航降采样不会覆盖原始记录，也不会把 VR 全量产品降成导航精度。全量代表保留相应重放流程的全部有效观测，并不意味着所有点都一定能获得颜色；相机不可见、遮挡、配对或质量不合格的点仍须保留真实状态。

在线 FAST-LIO 轨迹与离线密集重放轨迹可能不同。本版导航语义采用在线轨迹，与导航地图保持同源；不会把离线密集点的编号或过滤掩码直接套在导航几何上。两种估计轨迹不默认视为逐点完全对齐。

## 3. 原点、语义和执行边界

- 每次建图首个有效的底盘中心 O 位姿，登记为该场景原点 `(0, 0)`；对应出发车头方向登记为 `0°`。
- 地图选择不会假设车现在就在原点。切换地图后仍需要真实定位；旧路线、旧任务不能跨地图版本执行。
- YOLO 使用保存的同次 RGB-D，默认取最高 2 Hz 语义关键帧；这是语义计算采样率，不修改原始相机录制或全量着色输入。
- RGB 与深度只在同一相机启动 epoch 内配对，不复用深度，不允许相邻位姿之外的外推。记录相机设备时钟到主机时间的估计偏移；没有冒充硬件同步。
- 语义证据同时绑定地图 epoch、地图版本、语义版本与坐标系。物体图像、来源文件哈希与时间信息可追溯。
- 物体为历史候选，多帧支持不等于人工验收；“几何近邻”不自动解释成支撑关系、可抓取或现在仍存在。
- 本次没有重新估计外参。仍使用每次采集冻结的建图相机—雷达/车体配置，不借用机械臂抓取用途的新标定。
- 千问仍通过已有高层任务和导航执行接口工作，参数校验和执行联锁保留。修正了其把停止指令错误写成嵌套 `params`、以及控制接口不可用时仍强行生成低层停止指令的问题。

## 4. 并行和资源安排

原始记录、导航、语义、VR 后处理分属独立进程/服务。语义启动或计算失败不会取消导航校验，VR 着色失败不会停止原始录包。没有通过增加点数/帧数总上限来控制负载。

| 工作 | 调度 |
|---|---|
| 导航派生 | 同类型全局排队；Nice 5，CPUWeight 200，CPUQuota 200%，BLAS 2 线程 |
| 同场语义 | 独立排队；Nice 10，CPUWeight 50，CPUQuota 200%，MemoryHigh 4 GiB / MemoryMax 6 GiB；CPU 推理 |
| VR 全量重放与着色 | 较低优先级 Nice 15、CPUWeight 20、IOWeight 20，CPUQuota 400%，MemoryHigh 12 GiB |
| CPU 着色 | 按可用内存、CPU 核心与系统负载选 1～4 个工作进程 |
| GPU 着色 | 验证过的 ROCm 内核和设备；离线 GPU 锁；最多 2 个工作进程，内存不足或设备不可用时回退 CPU |

GPU 分支检查主机可用内存至少 8 GiB、设备可用内存至少 1.5 GiB；设备可用内存不足 4 GiB 时只用 1 个 GPU 工作进程。单次投影分块 100 万点，分块尺寸不是全场景点数上限。CPU/GPU 的已完成帧日志可以复用，重试不删除原始数据。

这些是资源隔离和启动时预算，不是所有服务的实时截止时间保证。后续长采集仍需观察实时视频/推理负载、磁盘余量和处理队列；本次没有重新进行一小时实车耐久测试。

## 5. AMD GPU 加速的实现与实测

复用了队友已安装的 ROCm 环境，没有更换驱动。实测设备是 Radeon 8060S。使用 PyTorch ROCm 加速坐标变换、RGB/鱼眼畸变投影、可见范围及投影质量计算；深度遮挡、优先级和颜色合并逻辑保留。

### A. 投影内核

100 万点、包含主机/设备数据往返，RGB 投影约 19.44 倍、鱼眼投影约 26.63 倍。这个数字仅是投影内核，不是整个着色任务加速比。双精度比较的点编号一致，浮点差异接近数值精度。

### B. 完整单帧着色

每帧输入 500 万真实场景点，包含图像解码、遮挡判断、取色和写盘：

| 输入 | CPU | GPU | 比率 |
|---|---:|---:|---:|
| RGB-D 彩色帧 | 0.994 s | 0.606 s | 1.64 倍 |
| 鱼眼帧 | 1.794 s | 0.520 s | 3.45 倍 |

### C. 进程级对比

8 个真实图像任务，每个处理 500 万点；不包含初次 ROCm 初始化的预热，包含完整帧处理：

| 配置 | 总时间 | 吞吐 |
|---|---:|---:|
| CPU 4 进程 | 3.861 s | 2.072 帧/s |
| ROCm 1 进程 | 3.444 s | 2.323 帧/s |
| ROCm 2 进程 | 2.071 s | 3.863 帧/s |

因此默认选择资源允许时 2 个 ROCm 工作进程，相对 CPU 4 进程实测 **1.86 倍**。点编号、RGB、颜色来源一致，质量权重在数值容差内一致。该结果不能直接外推成整场建图或一小时数据的端到端加速比；全量重放、索引、合并、导出仍有其他耗时。
