## 1. 方案概述

### 1.1 背景

具身智能（Embodied AI）要求智能体具备"感知—决策—执行"的物理闭环。
本平台以**轮式移动底盘 + 双六轴机械臂**为身体，以 **VR 头显遥操作**为入口，
构建"人在环路"的数智具身系统：操作员的全身动作实时映射为机器人动作，
机器人的位姿、关节状态与环境地图实时回传 VR 端，形成虚实融合的交互闭环。

### 1.2 物理任务定义（用于任务闭环成功率测量）

> **任务 T1（遥操作抓取搬运）**：操作员佩戴 VR 头显，遥控底盘移动至目标区域，
> 用右臂抓取桌上物体并放置到指定位置。一次成功 = 到达 + 抓取 + 放置全程无人工干预。
>
> **任务 T2（AI 辅助抓取，扩展）**：AI PC 端视觉模型识别目标物体并给出位姿建议，
> 操作员确认后机械臂自主执行抓取（人在环路的半自主模式）。

- 成功定义：物体离开原位并放置于目标区域，全程底盘/机械臂无失控
- 失败定义：掉物、碰撞、通信中断触发安全停止、超过 120 秒未完成
- 人工干预定义：任何直接触碰机器人或接管控制的行为
- 测试次数：每任务 ≥ 30 次有效测试

### 1.3 设计目标

1. **全身遥操作**：底盘移动 + 双臂操作 + 夹爪开合，一套 VR 装备统一控制
2. **实时回显**：机器人位姿、双臂关节、力反馈、环境点云地图回传头显
3. **中枢异构架构**：KR260 为物理数据中枢（全流量必经），AI PC 为感知决策中枢
4. **FPGA 实质贡献**：PL 承担硬件转发、时间戳、CAN 卸载、安全看门狗四项实时功能
5. **工程可维护**：容器化部署、模块化进程、自研轻量通信协议、可复用 Skill

### 2.2 关键数据流

| 数据流 | 路径 | 内容 | 频率/带宽 |
|---|---|---|---|
| VR 指令下行 | 头显 →(4G 特殊频段)→ 中继器 →(特殊频段)→ 接收器 →(网口)→ KR260 →(网口1)→ AI PC MergeNode | 双手 6DoF 位姿、底盘目标、夹爪、使能位图 | 78B/帧 |
| 控制指令分发 | AI PC →(UDP:6001)→ KR260 控制栈 | whole_body_msg | 50~100Hz |
| 状态回传 | KR260 →(UDP:6000)→ AI PC → KR260 →(接收器/中继器)→ VR | nav_state_msg（12 关节角+底盘位姿） | 50Hz，54B/帧 |
| 雷达上行 | MID-360 →(网口2)→ KR260 →(转发)→ AI PC FAST-LIO | 点云+IMU | ~20-30 Mbps |
| 里程计反馈 | AI PC（/filtered_odometry）→(UDP)→ KR260 底盘闭环 | 底盘实际位姿 | 50Hz |
| 地图回传 | AI PC 点云压缩 → KR260 →(网口)→ 接收器/中继器 → VR | Morton 增量分包 | 1400B MTU |

### 2.3 软硬件划分依据

- **KR260 PL**：纳秒级精度要求（时间戳）、独立于操作系统的安全逻辑（看门狗）、
  高速数据直通（转发网关/CAN 控制器）——硬件确定性与不可替代性是划分标准
- **KR260 PS**：周期控制（200Hz/20Hz）、运动学/动力学解算——实时但算法复杂，适合 CPU
- **AI PC**：SLAM、视觉检测、任务调度——算力密集、吞吐敏感，用 ROCm 端侧推理
- 跨机只传压缩后的指令与状态（78B/54B 帧），控制带宽需求 < 1 Mbps；
  大带宽数据（点云）在 KR260 内硬件直通，不进 PS 协议栈

## 3. 核心子系统

### 3.1 感知与定位（SLAM）—— 传感器接 KR260，算法在 AI PC

- **传感器**：Livox MID-360 激光雷达，网线接 KR260，点云+IMU 经 KR260 转发至 AI PC
  （过渡期 Linux 转发，最终由 PL 硬件直通）
- **算法**：FAST-LIO 激光惯性里程计（AI PC），输出 `/Odometry`（约 10 Hz）与 `/cloud_registered`
- **后处理**：滤波节点完成 FRD→FLU 坐标系转换 + 窗口 20 滑动平均，输出 `/filtered_odometry`
- **相机**：Orbbec Gemini 330 系列，USB 3.0 接 AI PC，彩色+深度+点云
- **端侧 AI**：Gemini 330 彩色流上部署轻量目标检测模型（YOLOv8n / INT8，ROCm 推理），
  输出目标位姿供 T2 半自主任务；报告 mAP@0.5:0.95、单样本延迟（预处理/推理/后处理分列）、FPS

### 3.2 遥操作通信（自研协议层）

- **架构**：asio 异步 I/O + 模板化双通道（UDP 跨机 / Unix socket 本机）+ 无锁环形队列
- **VR 接入**：头显经 4G 特殊频段到信号中继器，再由特殊频段接收器经网口接入 KR260，VR↔AI PC 双向流量由 KR260 中转
- **下行指令** `whole_body_msg`（78 字节/帧，含 CRC-16）：
  底盘目标位姿与速度、双手 6DoF 位姿与速度、左右夹爪、16 位使能位图
- **上行状态** `nav_state_msg`（54 字节/帧）：底盘实际位姿、双臂 12 关节角、左右臂力反馈
- **压缩编码**：3D 向量 10bit/分量定点、四元数 32bit smallest-three、量程化设计
- **时间同步**：AI PC 与 KR260 之间运行 PTP（linuxptp），PL 硬件时间戳对齐，
  为通信单向延迟测量提供时钟基准
- **异常处理策略**：
  - 指令帧 cnt 跳号/超时 >100ms → 双臂保持当前位置、底盘停车
  - AI PC 失联 → KR260 降级为 VR 直连模式（接收器经网口已在本地，仅保留遥操作）
  - 通信恢复 → 需操作员重新使能才继续（防突跳）
  - 所有异常事件写入日志，计入可靠性指标

### 3.3 双臂控制（KR260 PS 侧）

五层流水线：

```text
任务层  TeleopTaskRunner：mask 使能检查 → 位姿映射（×1.1放大+头显系换算）
        → 阻尼最小二乘 IK（λ=0.1，≤200 次迭代）→ 无解丢帧
规划层  ArmPlanner（20 Hz 硬周期）：线性插值铺轨迹，乒乓双缓冲无锁切换
控制层  ArmController（200 Hz 硬周期）：逆动力学前馈 τ = M(q)q̈ + C(q,q̇)q̇ + g(q)
硬件层  ArmHardwareInterface：SocketCAN 直发 Piper 协议（0x151/0x155/0x471…）
        支持单臂降级：任一臂离线只告警不退出
执行层  电机驱动器内部闭环（关节位置模式 / MIT 力控模式可切换）
```

仿真验证：同一套规划/控制器可切换至 MuJoCo 物理仿真接口，仿真先行再上真机。

**安全增强设计**：
- 跟踪误差保护：目标与实际位置误差持续超限 → 自动切 MIT 柔顺模式
  （重力补偿托住手臂，而非断电坠落）
- 力矩限幅：±45/±30/±20 N·m 分级限幅
- 双臂防碰：碰撞球模型（每臂约 15 个球）实时计算两臂最小间距，过近丢帧报警
- 关节位置/速度限幅表：J1 ±2.618rad，J2 0~π，J3 -2.967~0，J4 ±1.745，J5 ±1.22，J6 ±2.0944

### 3.4 底盘控制

- **状态机**（boost::sml）：unready / stop / moving（xy_control → yaw_control）/ free / terminate
- **控制律**：机体系下 PD 控制，先平移后转向；异常目标距离 ≥10m 自动停车
- **闭环反馈**：AI PC 的 `/filtered_odometry` 经 UDP 转发至 KR260（50Hz，
  链路延迟 1~2ms，相对底盘百毫秒级动态无感）
- **驱动**：SocketCAN `can0`（500 kbps），另支持车灯/喇叭 IO 控制

### 3.5 部署形态

AI PC 侧 Docker 容器化（每模块一容器，host 网络），ROS Master 固定 192.168.1.5:11311；
KR260 侧为裸 C++ 程序 + systemd 服务；
VR 侧经信号中继器（4G 特殊频段）与特殊频段接收器接入，接收器以网口连接 KR260。

## 4. KR260 侧设计（FPGA 设计质量 25 分——核心）

### 4.1 设计动因

| 动因 | 说明 |
|---|---|
| 实时性 | 双臂 200Hz 控制环置于专用嵌入式平台，不受感知负载干扰 |
| 中枢定位 | 所有流量物理上必经 KR260，PL 硬件转发/打戳是拓扑的自然延伸 |
| 算力分工 | AI PC 专注 SLAM/AI 大计算量任务；KR260（PS+PL）承接确定性控制 |
| 评分要求 | FPGA 承担转接板无法替代的硬件功能（3.2.2.1） |

### 4.2 选型结论

- **CAN 接入**：最终版为 PL 侧 CAN 控制器；过渡期为 USB-CAN 适配器，
  两者经 SocketCAN 统一抽象，软件零改动可互换
- **编译方式**：KR260 原生编译（Ubuntu 24.04，gcc 13），不引入交叉编译复杂度
- **通信**：自研协议层 UDP 跨机通道（CommChannel 模板原生支持）
- **ROS 依赖**：KR260 侧全部功能以裸 C++ 实现，不引入 ROS

### 4.3 调试工具（Skill 雏形）

- `tool` 命令行工具：单臂使能/失能/六关节位置下发
- `arm_control_gui.py` 图形化控制面板：六关节 ±0.1 rad 点动、目标/反馈实时显示、
  一键回零/失能、SSH 常驻通道下发
- `udp_arm_test.py`：UDP 通道联调监听脚本（帧率/丢包统计）
- `can_bringup_kr260.sh` + udev 规则：一键完成三路 CAN 配置（序列号绑定固定命名）
- 以上整理为 `skill/` 目录提交（加分项 3.2.2.5）

### 4.4 PL（FPGA 可编程逻辑）设计——四项

> 目标：让 KR260 的 FPGA 承担**实测可量化、转接板做不到**的硬件功能。
> 每项均给出"不可替代性"论证与量化指标。

#### 4.4.1 PL 硬件转发网关（核心）

- **内容**：PL 中实现端口间硬件分流——雷达点云流直通转发至 AI PC（不占 PS 协议栈）；
  VR/AI PC 的 UDP 控制流量在入口打时间戳后分流至 PS 或回传
- **为何不可替代**：KR260 是所有数据的物理必经节点；Linux 软件桥接每包增加
  数十微秒至毫秒级不确定延迟并占用 CPU，硬件转发延迟固定且为亚微秒级
- **量化指标**：转发延迟（PL vs Linux 桥对比）、持续吞吐率、PS CPU 占用对比
- **验证**：双口打流测试 + 时间戳单元测量
- **提交物**：Block Design tcl、.bit/.hwh、资源与时序报告、对比测量数据

#### 4.4.2 PL-CAN 控制器卸载

- **内容**：PL 中例化 CAN-FD 控制器（Xilinx 官方 IP），PS 侧以 SocketCAN 驱动访问
  （软件接口不变）；替换 USB-CAN 适配器
- **为何不可替代**：消除 USB 轮询调度抖动（实测可达毫秒级），发送时刻由 PL 硬件
  精确决定；三路 CAN 板载化
- **量化指标**：200Hz 控制帧发送周期 P99 抖动（PL vs USB 对比）、CPU 占用、
  截止期未命中率
- **验证**：`cangen` 压力测试 + 示波器/逻辑分析仪抓帧间隔波形
- **提交物**：Block Design tcl、.bit/.hwh、综合报告（LUT/FF/BRAM/WNS）、驱动加载脚本

#### 4.4.3 硬件时间戳单元

- **内容**：PL 中实现 100MHz 自由运行计数器，在每个 CAN 帧收发、UDP 包进出的
  硬件事件上打时间戳，经 AXI-Lite 供 PS 读取（~100 行 Verilog）
- **为何不可替代**：软件时间戳受内核调度影响（微秒到毫秒级不确定），硬件时间戳
  精度恒为 10ns；它是端到端延迟、通信 RTT 等所有指标的测量基准
- **量化指标**：时间戳分辨率、与 PTP 对齐后的同步误差（目标 < 1μs）
- **验证**：PL 时间戳 vs 示波器实测帧间隔比对

#### 4.4.4 低延迟安全看门狗

- **内容**：PL 中独立硬件状态机——监听 PS 心跳（AXI 寄存器定期喂狗）与 CAN 总线活动，
  PS 死机/控制环超时/总线异常时，不经过 Linux 直接接管：
  向三路 CAN 广播电机失能帧 + 底盘急停帧
- **为何不可替代**：纯软件看门狗在 Linux 卡死时同步失效；PL 状态机独立于 PS 运行，
  响应延迟微秒级且确定
- **量化指标**：异常注入测试下从异常发生到电机失能的延迟、安全状态触发成功率
  （≥30 次注入测试）
- **验证**：故障注入脚本 + 电机使能状态日志 + 示波器波形

#### 4.4.5 扩展候选（加分）

- 点云压缩卸载：Morton 编码器 PL 化，降低回传 VR 的带宽
- 10G Ethernet（SFP+）：高清视觉数据通道（对应 KR260 官方定位）

### 4.5 PL 开发路线

1. Vivado 搭 Block Design（Zynq PS + 各 AXI 模块），dtbo overlay / fpga-manager
   运行时加载，不重做系统镜像
2. 时间戳单元：简单 Verilog 实现（计数器 + AXI-Lite 从接口，百行级）
3. CAN 控制器：Xilinx 官方 CAN-FD IP，加载官方 SocketCAN 驱动
4. 转发网关：官方 AXI Ethernet MAC + 自写 UDP 解析分流状态机
5. 看门狗：纯 RTL 状态机，故障注入验证

## 5. 指标测量计划（对标 3.2.4）

### 5.1 核心必报指标

| 指标 | 测量方法 | 报告口径 |
|---|---|---|
| 任务闭环成功率 | T1/T2 各 30 次测试 | 成功/有效次数，附成功/失败/干预定义 |
| 端到端响应延迟 | 头显手柄动作（起点）→ 电机实际转动（终点）；PL 硬件时间戳打点 | P50/P95/P99/最大值 |
| AI 任务效果与推理性能 | Gemini 330 + YOLOv8n INT8：mAP@0.5:0.95；batch=1 延迟分列预处理/推理/后处理 | 单样本延迟 + FPS |
| FPGA 可量化贡献 | PL 转发 vs Linux 桥、PL-CAN vs USB-CAN 的延迟/抖动/CPU 对比；看门狗响应延迟；资源占用 | 实测数据 + 波形截图 |
| 通信性能 | VR↔KR260↔AI PC 全链路：PTP 对时后单向延迟、RTT、丢包率、指令超时率 | 分位数 + 持续 1 小时吞吐 |

### 5.2 场景专项指标（选报 3 项）

1. **实时控制**：200Hz 控制周期 P99 抖动、截止期未命中率、关节跟踪 RMSE
2. **FPGA 资源使用**：LUT/FF/BRAM/DSP 使用率 + WNS（结合性能说明合理性）
3. **系统可靠性**：连续运行时间（目标 ≥2h）、异常次数、人工干预次数、
   看门狗故障恢复时间、安全状态触发成功率

### 5.3 证据采集规范（对标 3.2.4.5）

- 每项指标注明：硬件型号、软件版本、FPGA 时钟频率、测试次数/时长、功耗模式
- 原始日志存 `metrics/logs/`，测试脚本存 `metrics/scripts/`，可重跑
- 延迟/抖动类附示波器或逻辑分析仪截图，存 `metrics/evidence/`
- 汇总表 `metrics/metrics.csv`，表头：指标名称/类别/数值/单位/测量条件/测试次数/证据文件

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| PL 开发进度 | FPGA 设计质量评分 | 四项按优先级分级，最小集为时间戳+看门狗（百行级 RTL）；CAN 用官方 IP 兜底 |
| 中继器/接收器链路稳定性（4G 特殊频段） | VR 接入 | 收发设备有线供电与固定部署；备用方案为接收器改接 AI PC、KR260 仅作有线中枢 |
| 特殊频段链路丢包/延迟（头显↔中继器↔接收器） | 遥操作卡顿 | 小包压缩协议（78B）、cnt 跳号检测、默认静止安全设计 |
| 力控前馈未启用 | 动态跟踪精度受限 | MIT 模式经 MuJoCo 仿真验证后启用 |
| KR260 内存有限（4GB） | 编译/运行资源紧张 | `-j2` 编译、裸 C++ 无 ROS、必要时加 swap |
| 头显侧程序不可控（源码缺失） | VR 链路重建 | 协议文档化 + 伪造数据脚本联调 |
| PL 改动影响已验证链路 | 回归风险 | 软件转发与 PL 转发双方案共存，可随时回退 |
