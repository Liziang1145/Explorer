# KR260 迁移实战教程
# 从 MobaXterm 连接开始，把双臂控制栈迁移到 KR260

> **目标**：把 `piper_dual_arm_teleop` 双臂控制栈从 AI PC 迁移到 KR260 上运行，
> CAN 采用 USB-CAN 适配器方案（软件零改动），通信从 Unix socket 改造为跨机 UDP。
> **前提**：KR260 已烧录 Ubuntu 22.04（Kria 官方镜像）并能上网；
> 你的 Windows 电脑与 KR260 在同一局域网（本教程中网段为 192.168.31.x）。
> **用法**：每章末尾有「检查点」，看到预期输出再进行下一章；不符合就停下来排错。

---

## 第 1 章 MobaXterm 连接 KR260

### 1.1 下载与安装

1. 官网下载免费家庭版：https://mobaxterm.mobatek.net/download.html
   （选 Home Edition, Installer 版）
2. 安装并打开。

### 1.2 建立 SSH 会话

1. 点击左上角 **Session** → 弹出窗口选 **SSH**
2. 填写：
   - **Remote host**：`192.168.31.130`（你的 KR260 局域网 IP，
     可在路由器后台或 KR260 上用 `hostname -I` 查看）
   - 勾选 **Specify username**，填 `ubuntu`（Kria 官方镜像默认用户）
   - **Port**：`22`
3. 点 OK，首次连接会问是否保存密码，选 Yes。
4. 左侧会自动弹出 **SFTP 文件浏览器**（图形化传文件，后面要用）。

> **可选**：勾选 X11-Forwarding（默认已开），可以在 Windows 上显示
> KR260 的图形窗口——但本教程全程命令行，不需要图形界面。

### 1.3 验证连接

连上后终端提示符变成类似 `ubuntu@kria:~$`，执行：

```bash
hostname -I        # 查看本机 IP
uname -m           # 应输出 aarch64（ARM64 架构）
```

**✅ 检查点 1**：看到 `aarch64`，且能看到 IP `192.168.31.130`。

## 第 2 章 环境检查（确认能编译 C++20）

在 SSH 终端执行：

```bash
echo "=== 系统 ==="; lsb_release -a 2>/dev/null | grep Description
echo "=== 编译器 ==="; gcc --version | head -1
echo "=== cmake ==="; cmake --version | head -1
echo "=== 内存 ==="; free -h | head -2
echo "=== 网络接口 ==="; ip -br link
echo "=== gs_usb ==="; lsmod | grep gs_usb || echo "gs_usb 未加载"
```

预期与判断：

| 项目 | 预期 | 不符合怎么办 |
|---|---|---|
| gcc | ≥ 11.x（Ubuntu 22.04 自带 11.x） | 低于 11：`sudo apt install gcc-11 g++-11` |
| 内存 | 总共约 3.5~4 GB | 正常，K26 就是 4GB |
| ip -br link | 有 eth0/eth1、lo、可能有 sit0 等 | 此时一般没有 can 接口，正常 |
| gs_usb | 未加载 | 正常，插上适配器后会自动加载 |

**✅ 检查点 2**：gcc ≥ 11，其余无异常。

> **不要在 KR260 上装 CLion 等大型 IDE**（4GB 内存扛不住）。
> 想用图形化编辑器，在 Windows 上装 VS Code + Remote-SSH 扩展，
> 连接 `ubuntu@192.168.31.130`，IDE 在 PC 上跑、编译在板子上跑。

## 第 4 章 在 KR260 上编译

### 4.1 安装编译工具

```bash
sudo apt update
sudo apt install -y build-essential cmake
```

### 4.2 编译

```bash
cd ~/piper_dual_arm_teleop
mkdir -p build && cd build
cmake ..
make deploy tool -j4
```

说明：

- `deploy` 是真机主程序（目标）；`tool` 是调试小工具
- `simulate`（MuJoCo 仿真）依赖 x86 预编译库，CMake 默认不编它，自动跳过
- 全部第三方库（asio/Eigen/spdlog）以头文件形式随源码携带，无需额外安装

预期输出结尾：

```text
[100%] Linking CXX executable deploy
[100%] Built target deploy
```

常见报错：

| 报错 | 原因 | 解决 |
|---|---|---|
| `gcc: internal compiler error` / 卡死 | 4GB 内存不够并行编译 | 改用 `make deploy -j2` |
| `error: 'concept' does not name a type` | gcc 版本太低 | 见第 2 章检查表 |
| `PROJECT_PATH` 相关警告 | 无害 | 忽略（它只是日志路径宏） |

**✅ 检查点 4**：`ls ~/piper_dual_arm_teleop/build/deploy` 存在。

## 第 5 章 USB-CAN 适配器接入

### 5.1 插上适配器并验证识别

插上**一只** USB-CAN 适配器（先插一只，逐个验证），执行：

```bash
dmesg | tail -8
ip -br link
```

预期 `dmesg` 里出现类似：

```text
gs_usb 1-1:1.0: Configuring for 1 interfaces
gs_usb 1-1:1.0 can0: firmware ...
```

`ip -br link` 里出现 `can0`。

如果没有出现：

```bash
sudo modprobe gs_usb          # 手动加载驱动
lsmod | grep gs_usb           # 确认加载成功
```

> 若 `modprobe` 报模块不存在（小概率），说明内核没编进 gs_usb，
> 备用方案：工程自带驱动源码 `robot_ws/usb_can_driver/gs_usb/`，
> 拷贝到 KR260 上 `make && sudo insmod gs_usb.ko`。

### 5.2 查序列号（为固定命名做准备）

每只适配器都要查一次序列号（一只一只插，或用不同 USB 口区分）：

```bash
udevadm info -a -n can0 | grep -m1 serial
# 输出类似: ATTRS{serial}=="003A002B3038561336343933"
```

把三只适配器的序列号分别记下来，标注哪个接底盘、哪个接左臂、哪个接右臂。

### 5.3 配置 udev 固定命名规则

编辑工作区里准备好的规则文件，把三个序列号填进去：

```bash
nano ~/kr260_setup/99-usb-can.rules
# 把 "填底盘适配器序列号" 等替换为上一步查到的真实序列号
```

安装规则并生效：

```bash
sudo cp ~/kr260_setup/99-usb-can.rules /etc/udev/rules.d/
sudo udevadm control --reload-rules
# 重新插拔三只适配器
ip -br link    # 应看到 can0、can1、can2 三只按规则命名
```

### 5.4 配置波特率并启用

```bash
sudo bash ~/kr260_setup/can_bringup_kr260.sh
```

预期输出：

```text
can0 (底盘, 500k) 已启用
can1 (机械臂, 1M) 已启用
can2 (机械臂, 1M) 已启用
```

> 注意：这个脚本每次重启后都要跑一次。稳定后可做成 systemd 服务
> （见第 9 章）。

**✅ 检查点 5**：`ip -br link` 显示 can0/can1/can2 均为 UP。

## 第 6 章 vcan 虚拟验证（无真臂也能跑）

真机械臂还没接时，用虚拟 CAN 先把程序跑起来。

### 6.1 建虚拟 CAN

```bash
sudo modprobe vcan
sudo ip link add dev vcan0 type vcan
sudo ip link set vcan0 up
sudo ip link add dev vcan1 type vcan
sudo ip link set vcan1 up
```

### 6.2 理解一个硬门槛

`deploy` 启动时会做两件事：
1. 检查 `/sys/class/net/can1`、`can2` 是否存在
2. 发送使能命令后，**循环 20 次等待 12 个电机使能反馈**，收不到就退出

用 vcan 验证时，需要另开一个终端模拟机械臂反馈帧。
最小模拟（让程序误以为电机已使能——状态字不含 DISABLED 位即可）：

```bash
# 另开一个 SSH 会话，循环发送低速反馈帧（0x261~0x266，data[5] 是状态字）
while true; do
  for id in 261 262 263 264 265 266; do
    cansend vcan0 2$id#0000000000000000
    cansend vcan1 2$id#0000000000000000
  done
  sleep 0.05
done
```

### 6.3 运行 deploy

```bash
cd ~/piper_dual_arm_teleop
sudo ip link set can1 down 2>/dev/null; sudo ip link set can2 down 2>/dev/null
# 临时让 deploy 用 vcan：修改 deploy.cpp 第 28 行
#   interface->start("can1", "can2")  →  interface->start("vcan0", "vcan1")
# 重新 make deploy 后：
sudo ./build/deploy
```

预期：日志打印 "Piper actuators enabled."，随后进入 200 Hz 控制循环
（程序在等 UDP/Unix 指令，没有指令时静默运行，`Ctrl+C` 退出）。
日志文件在 `~/piper_dual_arm_teleop/logs/`。

**✅ 检查点 6**：deploy 在 vcan 上启动成功不退出。

## 第 7 章 通信改造：Unix socket → UDP（核心步骤）

这是让 KR260 与 AI PC 对话的关键改造。原理：工程的 `CommChannel`
模板本身支持 UDP/Unix 两种模式，我们只需要换模板参数和构造参数。

### 7.1 KR260 侧：teleop_task_runner

**① 改成员类型**——打开 `include/teleop_task_runner.h`，找到
`channel_` 的声明（类似下面这行）：

```cpp
CommChannel<ChannelMode::Unix, NavStateSender, WholeBodyReceiver> channel_;
```

改为：

```cpp
CommChannel<ChannelMode::UDP, NavStateSender, WholeBodyReceiver> channel_;
```

**② 改构造参数**——打开 `src/teleop_task_runner.cpp`，找到第 45 行：

```cpp
channel_(this->io_context_, "/workspace/tmp/arm_solve", "/workspace/tmp/arm_station"),
```

改为（KR260 本地 6001 端口收指令，发往 AI PC 的 6000 端口）：

```cpp
channel_(this->io_context_, "192.168.31.130", 6001, "192.168.1.5", 6000),
```

> 注意：UDP 构造参数顺序是 (io, 本地IP, 本地端口, 远端IP, 远端端口)，
> 见 `comm_channel.hpp` 第 58 行。

### 7.2 AI PC 侧：MergeHandler

打开 `robot_ws/src/robot/include/communicate/MergeHandler.hpp`：

**① 改成员类型**（约第 48 行）：

```cpp
CommChannel<ChannelMode::Unix, WholeBodySender, NavStateReceiver> local_channel_arm;
```

改为：

```cpp
CommChannel<ChannelMode::UDP, WholeBodySender, NavStateReceiver> local_channel_arm;
```

**② 改两个构造函数里的初始化**（Unix 特化约第 78 行、UDP 特化约第 99 行）：

```cpp
local_channel_arm(io_context, param.arm_unix_channel_station, param.arm_unix_channel_solve),
```

改为（AI PC 本地 6000 端口，发往 KR260 的 6001）：

```cpp
local_channel_arm(io_context, param.merge_local_ip, 6000,
                  param.arm_remote_ip, param.arm_remote_port),
```

**③ 加配置参数**：在 `config.yaml` 里新增：

```yaml
arm_remote_ip: 192.168.31.130   # KR260 地址（联调时改静态 IP 后同步改）
arm_remote_port: 6001
```

并在 `configParser.hpp` 的 `param_t` 里照着现有字段的写法加两个成员
（参照 `merge_remote_ip`/`merge_remote_port` 的解析方式各加一段）。

### 7.3 通道对应关系（改完后）

```text
AI PC MergeHandler                    KR260 TeleopTaskRunner
  6000 发 whole_body_msg ──────UDP────► 6001 收（原 arm_solve 方向）
  6000 收 nav_state_msg  ◄─────UDP────── 6001 发（原 arm_station 方向）
```

> 简化设计：每侧一个端口同时收发（CommChannel 本来就是单 socket 双向），
> 只需 6000/6001 两个端口。

### 7.4 联调测试

1. AI PC 侧改完后重新编译 robot 包，启动 MergeNode
2. KR260 侧重新 `make deploy`，启动
3. AI PC 上 `sudo tcpdump -i any udp port 6000 -X` 应看到双向报文
4. 双臂侧日志应打印 IK 求解结果（当头显指令到来时）

**✅ 检查点 7**：tcpdump 看到双向 UDP 流量，KR260 日志有正常输出。

## 第 8 章 真臂联调

1. 接线：左臂 CAN → can1 适配器，右臂 CAN → can2 适配器，注意 CAN_H/CAN_L/GND
   与 120Ω 终端电阻
2. 把 `deploy.cpp` 里的 `start("vcan0", "vcan1")` 改回 `start("can1", "can2")`，
   重新编译
3. `sudo bash ~/kr260_setup/can_bringup_kr260.sh` 启用总线
4. `candump can1` 应能看到机械臂上电后的周期性反馈帧（0x251~0x256）
5. 运行 `sudo ./build/deploy`，确认 12 个电机使能成功
6. AI PC 侧从头显发控制指令，先小幅度验证单臂跟随，再双臂

安全提醒：首次真臂联调务必有人守着急停，运动范围清空。

## 第 9 章 收尾：开机自启（systemd）

### 9.1 CAN 自启服务

```bash
sudo tee /etc/systemd/system/can-bringup.service <<'EOF'
[Unit]
Description=Bring up CAN interfaces
After=network.target

[Service]
Type=oneshot
ExecStart=/bin/bash /home/ubuntu/kr260_setup/can_bringup_kr260.sh
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl enable can-bringup.service
```

### 9.2 双臂程序自启

```bash
sudo tee /etc/systemd/system/dual-arm.service <<'EOF'
[Unit]
Description=Piper dual arm teleop
After=can-bringup.service

[Service]
ExecStart=/home/ubuntu/piper_dual_arm_teleop/build/deploy
WorkingDirectory=/home/ubuntu/piper_dual_arm_teleop
Restart=on-failure

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl enable dual-arm.service
```

> 建议联调阶段先不要 enable dual-arm，手动启动便于观察日志；
> 稳定后再开自启。

## 附录 B 故障速查表

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 插适配器无 can 接口 | gs_usb 未加载 | `sudo modprobe gs_usb` |
| 三只适配器编号乱 | udev 规则未生效 | 检查序列号是否抄对，`udevadm control --reload` 后重插 |
| deploy 卡在使能 | 电机反馈帧收不到 | `candump` 看总线有没有帧；查 CAN_H/L 是否接反、终端电阻 |
| deploy 报接口不存在 | can1/can2 未启用 | 先跑 can_bringup 脚本 |
| AI PC 收不到 KR260 的包 | IP/端口不对称 | 对照 7.3 通道表核对两侧四个参数 |
| 编译卡死 | 内存不足 | `make -j2` 或加 swap |
